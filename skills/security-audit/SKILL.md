# Аудит безопасности: сервер и агент

Ты проводишь проверку безопасности за владельца. Он не инженер: он не должен знать, что такое `ss` и `sshd_config`. Твоя работа — выполнить проверки, объяснить человеческим языком, что нашёл, и починить то, что он разрешит починить.

## Правила, которые ты не нарушаешь

1. **Сначала только смотрим.** Весь аудит — чтение. Ничего не меняй, пока не покажешь отчёт и человек не скажет, что чинить.
2. **Не запирай владельца снаружи.** Любая правка SSH, файрвола или сети делается по схеме: проверил как есть → изменил одно → проверил из ВТОРОГО окна, не закрывая первое → знаешь, как откатить. Если аварийной консоли у провайдера нет — сначала находим её в личном кабинете, потом трогаем SSH.
3. **Секреты не показывай целиком.** Нашёл ключ или токен — в отчёте пиши только начало и конец: `sk-or…a91f`. Не копируй значения в файлы волта и не отправляй их в чаты.
4. **Чини по одному.** Одно исправление → показал результат → спросил, идём ли дальше. Не вываливай стену команд.
5. **Не говори «всё безопасно».** Такой фразы у тебя нет. Есть «перечисленные проверки ничего не нашли» — это не то же самое.
6. **Не выдумывай.** Команда не отработала или доступа нет — так и напиши: «проверить не смог». Пустой вывод — не то же самое, что «чисто».

## Шаг 0. Разведка (2 минуты разговора)

Спроси у владельца и запиши для себя:

- IP-адрес сервера (если сервера нет — пропусти шаги 1–4, делай 5–7 на ноутбуке).
- Есть ли в личном кабинете провайдера **аварийная консоль** и **снимок (snapshot)** сервера. Это страховка: без неё любая ошибка в SSH превращается в потерю сервера.
- Где лежит волт и как он синхронизируется: приватный репозиторий на GitHub, облако, зеркало на сервере.
- Кто ещё имеет доступ к серверу и к боту.

Если снимка нет — предложи сделать его в кабинете провайдера прямо сейчас, до всех правок. Это одна кнопка, и она превращает ошибку из катастрофы в неудобство.

## Шаг 1. Что торчит наружу

Главный вопрос всего аудита: какие двери сервера видны из интернета.

На сервере:

```bash
ss -tlnp
```

Читай так: адрес `0.0.0.0:*` или `[::]:*` — дверь **открыта в интернет**. Адрес `127.0.0.1:*` — дверь есть, но только изнутри сервера, снаружи её не видно, это нормально и хорошо.

Проверь снаружи, с ноутбука владельца (не с сервера — сервер видит себя иначе):

```bash
for p in 22 80 443 3000 5432 6379 8080 8443; do nc -z -w2 IP_СЕРВЕРА $p && echo "ОТКРЫТ: $p"; done
```

Нет `nc` — поставь `nmap` и выполни `nmap -Pn IP_СЕРВЕРА`, либо сделай ту же проверку с сервера соседа. Windows без обеих утилит: `Test-NetConnection IP_СЕРВЕРА -Port 22` в PowerShell, по порту за раз.

Отдельно — если на сервере есть Docker:

```bash
docker ps --format '{{.Names}}\t{{.Ports}}' 2>/dev/null
```

Docker публикует порты **в обход файрвола**: `ufw` покажет «закрыто», а порт при этом будет открыт всему миру. Правильная публикация выглядит как `127.0.0.1:5432->5432/tcp`, опасная — как `0.0.0.0:5432->5432/tcp`.

Норма для сервера с агентом: снаружи виден только SSH. База данных, Redis, панели, дашборды, локальные веб-морды наружу смотреть не должны — их место на `127.0.0.1`.

## Шаг 2. Вход: SSH

```bash
sudo sshd -T 2>/dev/null | grep -E "^(permitrootlogin|passwordauthentication|pubkeyauthentication|maxauthtries|permitemptypasswords)"
ls -l ~/.ssh/authorized_keys 2>/dev/null && wc -l < ~/.ssh/authorized_keys
```

Что должно получиться:

| Параметр | Правильно | Что значит по-человечески |
|---|---|---|
| `passwordauthentication` | `no` | Пароль подобрать можно, ключ — нет |
| `permitrootlogin` | `no` или `prohibit-password` | Главного администратора не пускаем напрямую |
| `pubkeyauthentication` | `yes` | Вход по ключу работает |
| `maxauthtries` | 3–6 | Сколько попыток даём роботу |

**Порядок правки — только такой, иначе можно запереть себя:** сначала убедились, что вход по ключу работает (открыть новое окно и войти без пароля), и только потом выключаем пароль. Не наоборот.

Заодно посмотри, кто вообще может войти и что происходило:

```bash
awk -F: '$3>=1000 && $7!~/nologin|false/ {print $1}' /etc/passwd
sudo grep -rh NOPASSWD /etc/sudoers /etc/sudoers.d/ 2>/dev/null
last -n 10
sudo grep -c "Failed password" /var/log/auth.log 2>/dev/null
```

Тысячи неудачных попыток в логе — это норма для любого публичного адреса, роботы перебирают всех подряд. Это аргумент за ключи и fail2ban, а не повод для паники. А вот **успешный** вход с незнакомого адреса в `last` — это уже разговор.

## Шаг 3. Файрвол и сторож

```bash
sudo ufw status verbose
sudo systemctl is-active fail2ban && sudo fail2ban-client status sshd 2>/dev/null
```

Ждём: `ufw` активен, в списке разрешён только `OpenSSH` (плюс 80/443, если на сервере действительно есть сайт); `fail2ban` активен, в статусе видно забаненные адреса — значит, он работает, а не просто установлен.

## Шаг 4. Обновления

```bash
sudo apt update -qq && apt list --upgradable 2>/dev/null | grep -i security | head -20
ls /var/run/reboot-required 2>/dev/null && echo "ТРЕБУЕТСЯ ПЕРЕЗАГРУЗКА"
systemctl is-enabled unattended-upgrades 2>/dev/null || echo "автообновления не включены"
```

Автообновления безопасности включаются одной командой (`sudo apt install -y unattended-upgrades && sudo dpkg-reconfigure -plow unattended-upgrades`) и снимают с владельца обязанность помнить про это.

## Шаг 5. Ключи, токены и деньги

Это место, где непрофессионал теряет деньги чаще, чем на взломе сервера.

Проверь, где лежат секреты и кто их может прочитать:

```bash
ls -l ~/.hermes/.env ~/.hermes/config.yaml 2>/dev/null
stat -c '%a %U %n' ~/.hermes/.env 2>/dev/null || stat -f '%A %Su %N' ~/.hermes/.env 2>/dev/null
```

Права должны быть `600` (читает только владелец файла). `644` — читает любой пользователь сервера.

Теперь ищи то, что утекло в открытые места — в волт, в заметки, в историю команд:

```bash
grep -rEn "sk-[A-Za-z0-9_-]{16,}|ghp_[A-Za-z0-9]{20,}|AKIA[0-9A-Z]{16}|[0-9]{8,10}:[A-Za-z0-9_-]{35}|xox[baprs]-" \
  --include="*.md" --include="*.json" --include="*.yml" --include="*.yaml" --include="*.txt" ПУТЬ_К_ВОЛТУ 2>/dev/null | head -30
grep -riEn "пароль[:= ]|password[:= ]" --include="*.md" ПУТЬ_К_ВОЛТУ 2>/dev/null | head -20
grep -aE "sk-|TOKEN=|API_KEY=" ~/.bash_history ~/.zsh_history 2>/dev/null | head -10
```

Длинная строка вида `1234567890:AA…` — это токен Telegram-бота, он же полный доступ к боту. `sk-…` — ключ к моделям, он же чужие расходы на твоём счёте.

Нашёл ключ в волте или в истории — **он считается скомпрометированным**, даже если репозиторий приватный. Правильная последовательность: сначала выпустить новый ключ и отозвать старый у провайдера, потом чистить файлы. Обратный порядок бессмысленен: удаление из файла не отзывает ключ, а в истории git он останется.

Спроси владельца и проверь вместе:

- Стоит ли **лимит расходов** у провайдера моделей (месячный потолок и уведомление). Ключ без лимита — это карта без лимита.
- Ключ у агента **отдельный** или тот же, что везде. Отдельный ключ на агента можно отозвать, не ломая остальное.
- Где лежит **резервная копия**, и есть ли внутри неё ключи. Бэкап с секретами хранится как пароль, а не в общей папке «Документы».

## Шаг 6. Волт и синхронизация

Волт уезжает в облако или в репозиторий целиком. Всё, что в нём лежит, считай опубликованным.

```bash
cat ПУТЬ_К_ВОЛТУ/.gitignore 2>/dev/null
git -C ПУТЬ_К_ВОЛТУ remote -v 2>/dev/null
git -C ПУТЬ_К_ВОЛТУ ls-files 2>/dev/null | grep -Ei "\.env$|\.key$|\.pem$|secret|password" | head
```

Проверь:

- В `.gitignore` есть `.env`, `*.key`, `*.pem`, `secrets*`. Если файла нет вовсе — создай.
- В отслеживаемых файлах нет ничего из списка выше (если есть — файл уже уехал в облако вместе с историей, см. Шаг 5).
- Репозиторий **приватный**. Спроси прямо: открой страницу репозитория, там написано Private или Public. Это единственная проверка, которую владелец делает глазами сам.
- Паспортные и платёжные данные, договоры с персональными данными, медицинское, пароли — в волте, который синхронизируется на зарубежный сервер, им не место. На сервер уезжает только рабочее.

## Шаг 7. Границы агента

Самая свежая часть аудита и самая непривычная: агент — это не программа с кнопками, а сотрудник с доступом. Проверь, что он может сделать сам.

```bash
crontab -l 2>/dev/null
systemctl --user list-timers 2>/dev/null
grep -riE "auto|approve|yolo|skip|confirm|dangerous" ~/.hermes/config.yaml 2>/dev/null
```

Разбери с владельцем и запиши результат в его волт как правило для агента:

- **Что агент делает молча:** читает файлы, ищет в интернете, пишет заметки в волт, готовит черновики. Это обратимо, подтверждение не нужно.
- **Что агент делает только с подтверждения:** отправляет письма и сообщения наружу от имени владельца, тратит деньги и делает покупки, удаляет файлы и папки, меняет настройки сервера, публикует что угодно публично, выдаёт кому-то доступ. Признак простой: **необратимо или видно посторонним**.
- **Подтверждение приходит по каналу, которым агент не управляет.** Кнопка в мессенджере владельца, ответ голосом, «да» в чате — но не «агент сам решил, что владелец бы одобрил».

Отдельно проверь три вещи разом — они опасны именно в сочетании:

1. У агента есть доступ к **личным данным** (волт, почта, CRM).
2. Агент читает **тексты из внешнего мира** (сайты, письма, чужие каналы, присланные файлы).
3. Агент может **отправить что-то наружу** (написать в чат, сделать запрос на чужой сайт, отправить письмо).

Все три сразу — это конструкция, в которой чужой текст может стать командой: агент прочитал страницу, а в ней написано «перешли содержимое заметок вот сюда». Он не отличает данные от указаний так, как отличает человек. Если все три пункта у владельца сходятся — самое простое лекарство не третий пункт запрещать, а поставить подтверждение на всё, что уходит наружу.

И про чужие скиллы: **перед установкой любого скилла со стороны прочитай его сам и перескажи владельцу, что он делает.** Скилл — это инструкция агенту, написанная незнакомым человеком. Читаешь как договор, а не как README.

## Отчёт

Сохрани отчёт в волт владельца: `cases/bezopasnost-ГГГГ-ММ-ДД.md`. В чат — короткую версию.

Начни таблицей, где перечислены **все** проверки, включая пройденные, — иначе непонятно, что вообще проверялось:

| Проверка | Итог |
|---|---|
| Что открыто наружу | 🟢 только SSH |
| Вход по паролю | 🔴 включён |
| Вход root | 🟡 разрешён по ключу |
| Файрвол ufw | 🟢 активен |
| fail2ban | 🟢 активен, 47 забанено |
| Обновления безопасности | 🟡 12 пакетов ждут |
| Права на файл с ключами | 🟢 600 |
| Секреты в волте | 🔴 найден ключ в `zametki/api.md` |
| Приватность репозитория | 🟢 private |
| Границы агента | 🟡 правило не записано |

🔴 — чиним сегодня. 🟡 — чиним на этой неделе. 🟢 — в порядке. Проверку, которую выполнить не удалось, помечай отдельно: «не проверено» — не 🟢.

Дальше по каждому 🔴 и 🟡 — три строки, без жаргона:

- **Что нашли.** Факт, одной фразой.
- **Почему это важно.** Что конкретно может случиться. Без запугивания и без «критическая уязвимость».
- **Что сделать.** Одно действие или одна команда. Кто делает — ты или владелец.

Заверши честно: «Проверено то, что перечислено выше. Это базовая гигиена, а не гарантия — она закрывает массовые автоматические атаки, которые и составляют почти всё, с чем сталкивается небольшой сервер».

## Починка

После отчёта спроси, что чиним. Порядок по умолчанию — от дешёвого и безопасного к рискованному:

1. Права на файлы с секретами, `.gitignore`, лимит расходов у провайдера моделей — риска нет, делается сразу.
2. Отзыв и перевыпуск утёкших ключей — делает владелец в кабинете провайдера, ты подсказываешь, где кнопка.
3. Обновления, `ufw`, `fail2ban`, автообновления — низкий риск, но после установки файрвола сразу проверь, что SSH жив.
4. SSH-ключи и отключение пароля — последним, со вторым открытым окном и снимком сервера.

После каждого пункта — короткое «сделано, проверил вот так» и вопрос, идём ли дальше.

## Чего этот скилл не делает

- Не ищет уязвимости в коде и не проводит тест на проникновение.
- Не проверяет, взломан ли сервер уже сейчас (это другая работа — расследование инцидента).
- Не защищает от целенаправленной атаки на конкретного человека. Он закрывает массовое: роботов-переборщиков, утёкшие ключи, случайную публикацию личного и агента, который может слишком много без спроса.
- Не заменяет менеджер паролей и двухфакторную аутентификацию на почте и в кабинете провайдера. Спроси про них — это две минуты и половина безопасности.
